第 11 章 项目导览：需求、架构与工程初始化

一句话总结：读懂 Ticket Polit 的需求与技术方案，理解「两个数据库、三层结构」的架构决策，搭好前后端骨架并完成首次联通。

从这一章开始，玩法变了

前十章是一个概念一个概念地学，每章的代码只服务当章的理解。从本章起，我们换一个推进方式：围绕一个真实产品的功能切片，把学过的所有东西组装起来。 概念不再是主角，「用户要用这个功能，怎么实现」才是。

这意味着两件事。一是代码量上来了，单章会出现多个文件、跨前后端的完整链路——别慌，每一段我们都会讲清它在系统里的位置。二是你会遇到前十章没细讲的工程话题：Express 中间件、SQLite、SSE 协议、Vue 组件、构建部署。默认你懂基础语法，但这些「架构层面的复杂内容」我们会展开讲。

需求：Ticket Polit 是个什么产品

Ticket Polit（工单副驾驶）是一个企业内部服务台系统。故事是这样的：公司里的员工遇到问题——报销不会填、VPN 连不上、要申请退款——传统做法是提一个工单，等服务台同事逐条处理。服务台就两个人，工单永远积压，员工永远在催。

Ticket Polit 的思路是 AI 先接一道：工单进来，AI 工作流先判断类型，能直接答的立刻答，要审批的走审批流，真需要人的才转人工。系统里有两个角色：

  • 员工：提交工单、查看自己的工单、在工单下追问；
  • 审批员：在审批中心处理高风险操作的批准/拒绝（本项目里就是退款）。

核心流程三条路，这就是整个产品的灵魂：

  1. 咨询类（「报销额度是多少」「VPN 怎么连」）：AI 检索知识库，直接生成回复，工单办结；
  2. 退款类：AI 整理出处理方案，但必须人工审批，批准前绝不执行，批准后执行并告知结果；
  3. 其他类（报修、投诉等）：AI 登记分类，转人工队列，告知员工预计响应时间。

注意这三条路对应了你前十章学过的三种能力：RAG（第 3 章）、interrupt 人工审批（第 9 章）、确定性条件分支（第 7 章）。这不是巧合——真实产品的功能切片，就是框架能力的排列组合。

明确不做什么

好项目和烂项目的区别往往不在做了什么，而在敢不做什么。本项目砍掉：用户注册与 SSO（用预置 token 模拟登录）、权限矩阵（硬编码两个角色）、附件与富文本、通知推送、知识库管理后台（知识库就是三份本地 Markdown）。每一刀都是为了让五章的篇幅聚焦在 AI 全栈的主干上。真实项目里这些都该做，但那是另一个五章的事。

从需求到图：AI 内核的设计

第 5 章教过「把业务流程翻译成节点和边」，现在对真实需求做一遍：

flowchart LR S(["工单提交/追问"]) --> C["classify 分类"] C -->|consult 咨询| R["consult 检索知识库并回复"] --> E(["办结"]) C -->|refund 退款| A["refundFlow 整理方案并等待审批"] A -->|批准| X["执行退款并回复"] --> E A -->|拒绝| N["告知未通过"] --> E C -->|other 其他| H["handoff 转人工"] --> E

对照需求逐条翻译：「AI 先判断类型」是 classify 节点加条件边；三条路径各是一个节点；「必须人工审批」是 refundFlow 里的 interrupt；「员工可以追问」意味着整个图要能多轮运行——第 8 章的 Checkpointer，thread_id 就是工单 ID。

State 设计沿用第 10 章的混合形态（业务字段 + 消息轨迹），到第 13 章你会看到它的完整定义。现在先记住原则：分类结果、工单 ID 这类流程数据进业务字段，对话历史进 messages。

架构总览：两个数据库是重点

整个系统三层：Vue 前端、Express 后端、LangGraph AI 内核（跑在后端进程里）。数据却有两处存放，这是新手最容易糊涂的地方：

flowchart TB subgraph FE["Vue 前端（浏览器）"] UI["提交页 / 列表页 / 详情页 / 审批中心"] end subgraph BE["Express 后端（Node 进程）"] API["REST API 层"] AG["LangGraph 工作流"] end DB1[("业务库 tickets.sqlite<br/>better-sqlite3")] DB2[("流程状态 checkpoints.sqlite<br/>SqliteSaver")] KB[/"知识库 knowledge/*.md"/] UI -->|"HTTP / SSE"| API API --> AG API --> DB1 AG --> DB2 AG --> KB

业务库存业务事实：工单标题、描述、分类、状态、提交人。它的读者是人和业务代码——列表页展示、状态筛选、以后做报表统计都靠它。流程状态库（checkpointer）存 Agent 执行状态：每个工单的处理流程走到哪一步、中间 State 是什么、断点在哪。它的读者只有 LangGraph 框架。

为什么要分两处？因为它们的生命周期和访问模式完全不同。业务数据要长期保存、要被各种查询；流程状态跟着 Agent 走、结构由框架定、人基本不直接读。第 8 章的误区一说的就是这事：Checkpointer 不是业务数据库。混在一起放，业务查询会被框架的存储结构绑架，框架升级时业务数据还受牵连。

知识库是三份 Markdown 文件（报销制度、IT 指南、请假制度），服务启动时建成内存向量索引（第 3 章的 MemoryVectorStore）。数据量小，没必要上独立向量库——这是选型，不是偷懒。

技术选型：每个选择的理由

选择理由放弃了什么
Express 5Node 最主流的 Web 框架，中间件模型直白，教学零障碍NestJS（太重）、Hono（生态年轻）
better-sqlite3嵌入式、零部署、同步 API 对教学友好，单机产品完全够用Postgres（要起服务，分散焦点）
Vue 3 + Vite上手曲线平缓，script setup 写法和 TS 配合好React（等价选择，口味问题）
SSE 流式单向推送（后端→前端）场景的最简方案，HTTP 原生WebSocket（双向，杀鸡用牛刀）
不引 Pinia本项目共享状态就两个数组，reactive 模块足够组件库同理，聚焦 AI 交互

SSE 和 WebSocket 这一条值得展开半句：我们的流式需求是「后端把 Agent 过程推给前端」，纯单向。SSE 就是 HTTP 响应不关门、持续写数据，浏览器原生支持、自动重连、实现十行以内。WebSocket 解决的是双向实时（聊天室、协同编辑），用它得处理连接管理、心跳、协议设计——为了单向推送背这些，不值。选型不是选最强的，是选刚好够的。

开工。结构是前后端同仓（monorepo 的极简形态）：

里程碑 0：前后端首次联通

骨架阶段的目标只有一个：浏览器里的页面能调到后端的接口。先写最小的后端 src/index.ts：

import express from "express";

const app = express();
app.use(express.json());

app.get("/api/health", (_req, res) => {
  res.json({ ok: true, service: "ticket-polit", time: new Date().toISOString() });
});

app.listen(3000, () => console.log("server on http://localhost:3000"));

express() 创建应用，app.get 注册「GET /api/health 这个路由由这个函数处理」，res.json 返回 JSON。启动：

npx tsx --env-file=.env src/index.ts
# curl http://localhost:3000/api/health 应返回 {"ok":true,...}

前端用 Vite 脚手架（在 ticket-polit 目录下）：

npm create vite@latest web -- --template vue-ts
cd web && npm install && npm install vue-router@4

跨域与代理：开发期的必修课

前端跑在 localhost:5173（Vite 默认），后端在 localhost:3000。浏览器有同源策略：页面来自 5173，却去请求 3000，默认会被拦（这就是 CORS 问题）。解决办法有两派：后端发 CORS 头放行，或前端开发服务器做代理。开发期用代理更干净——在 web/vite.config.ts 里加：

import { defineConfig } from "vite";
import vue from "@vitejs/plugin-vue";

export default defineConfig({
  plugins: [vue()],
  server: {
    proxy: {
      "/api": "http://localhost:3000",   // 前端代码里请求 /api/*，Vite 替你转给 3000
    },
  },
});

配了这个，前端代码里永远写 /api/health 这样的相对路径，不用关心后端在哪；浏览器的请求都发给 5173，同源策略不触发，Vite 在服务器侧转发（服务器之间没有同源限制）。生产环境的对应方案是「前后端同域部署」，第 15 章落地。

把 web/src/App.vue 改成最简单的验证页：

<script setup lang="ts">
import { onMounted, ref } from "vue";
const health = ref("请求中…");
onMounted(async () => {
  const r = await fetch("/api/health");
  const j = await r.json();
  health.value = `后端在线：${j.service} @ ${j.time}`;
});
</script>

<template>
  <h1>Ticket Polit</h1>
  <p>{{ health }}</p>
</template>

<script setup> 是 Vue 3 的组合式写法：里面的顶层变量、函数直接能在模板里用；ref 创建响应式数据——值一变，用到它的模板自动更新；onMounted 是组件挂载后执行的生命周期钩子。这三个概念撑起了本项目的全部前端。

npm run dev 起前端，浏览器打开 http://localhost:5173，看到「后端在线：ticket-polit @ …」，里程碑 0 达成。

本模块的开发纪律

五章五个里程碑，每章结束都有可验证的验收动作（M0 就是刚才那个「看到后端在线」）。跟练的建议：

  • 按章验收，不跳步。后面每一章都建立在前一章的代码上，跳一章后面全是隐形坑。
  • 代码先手敲再对照。项目代码比前十章长，复制粘贴能跑，但你的肌肉记忆是零。
  • 报错了先看在哪家。前端报错在浏览器控制台（F12），后端报错在终端，SSE 问题看 Network 面板的 EventStream——第 15 章有专门的排错清单，但定位习惯从现在开始养。

小结

本章完成了从「学概念」到「做产品」的切换：读懂 Ticket Polit 的三条 AI 路径需求，把它翻译成 LangGraph 的图设计；建立了「前端 / 后端 / AI 内核」三层加「业务库 / 流程状态库」两个数据库的架构认知；说清了每个技术选型的理由；搭好骨架并通过 Vite 代理完成前后端首次联通。

自测

  1. 业务库和流程状态库存的分别是什么？为什么不合并？
  2. 「退款必须人工审批」这个需求，在图设计上对应什么机制？在数据上对应什么字段？
  3. 开发期为什么用 Vite 代理而不是让后端发 CORS 头？生产环境对应的方案是什么？
  4. SSE 和 WebSocket 的适用差异是什么？本项目为什么选 SSE？

参考答案：1. 业务库存业务事实（工单内容、状态），流程状态库存 Agent 执行快照；两者生命周期与访问模式不同，合并会让业务查询被框架存储结构绑架。2. 对应 refundFlow 节点内的 interrupt；数据上对应工单的 status（pending_approval）与审批结果字段。3. 代理让前端只用相对路径、不触发同源策略，且部署拓扑变化时前端代码不动；生产用前后端同域部署。4. SSE 是 HTTP 单向推送，适合后端到前端的流式；WebSocket 是双向长连，适合聊天协同。本项目只需把 Agent 过程推给前端，SSE 最简。
