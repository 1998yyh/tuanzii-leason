第 1 章 RAG 是什么：大模型的三大硬伤与三种解法

一句话总结：从幻觉、时效性、私域知识三个翻车现场出发，搞懂 RAG 到底解决什么问题，以及它和 Fine-tuning、Prompt Engineering 各自适合什么场景。

三个翻车现场

很多人第一次用大模型做正经事，兴奋劲维持不过三天。不是模型不聪明，而是它会在你意想不到的地方掉链子。先看三个几乎每个人都遇到过的场面。

现场一：它编了一个不存在的 API

你在写一个调用模型的小程序，问它：「openai 这个 npm 包里，有没有 createAndPoll 这个方法？给我个例子。」

它立刻给出一段代码，有模有样，参数注释一应俱全：

// 它给你的答案（注意：这个方法是编的）
const run = await client.chat.completions.createAndPoll({
  model: "glm-4.7-flash",
  messages: [{ role: "user", content: "你好" }],
});

你抄进项目，一运行，报错：client.chat.completions.createAndPoll is not a function。翻遍官方文档，这个方法根本不存在。

问题不在于它答错了，而在于它答得自信。没有犹豫，没有「我不确定」，代码格式漂亮得像从文档里抄的。你差点就信了。

现场二：它不知道昨天发生了什么

你问：「上周发布的那款新手机，起售价多少？」

它要么老实说「我的知识有截止时间」，要么更糟——把上一代的价格当成新闻报给你，语气笃定得像刚看完发布会：「这款新机起售价 4999 元，提供三个存储版本。」价格是真的，型号是上一代的，张冠李戴得毫无痕迹。模型不是联网的新闻客户端，它知道的一切都冻结在训练数据截止的那一天。那一天之后的世界，对它来说还没发生。

现场三：它答不出你公司的报销制度

你把问题换成自己真正关心的：「我们公司的差旅住宿标准是多少？」

这个问题一点都不难，答案就躺在公司内网那份 PDF 里。但模型训练时没见过这份文件，对它来说这是天书。它可能给你编一个「业内常见标准」，又是那种自信的、看起来合理的胡说。

「私域知识」这个词值得多停留一秒。它泛指一切没进过模型训练语料、但你又需要模型知道的内容：公司内部的制度、文档、工单、代码仓库；你个人的笔记、收藏、聊天记录；某个团队积累的研究资料、实验数据。这些内容的共同点是有价值、不公开、还经常更新，恰好每一条都踩在模型的盲区上。对绝大多数想把大模型用起来的团队来说，真正的业务问题几乎都藏在这类知识里。

术语地基：先把五个词说清

继续往下之前，有五个词会反复出现，现在一次说清。已经熟悉的可以快速扫过。

LLM（Large Language Model，大语言模型）：你平时用的 GPT、GLM、Claude、DeepSeek 都是。它的工作方式粗暴地讲就一件事：给定前面的文字，预测下一个最可能出现的词。别小看这个「接龙」，万亿级参数学出来的接龙，表现出了惊人的理解和生成能力。但它的全部知识都来自训练时见过的文本，这个出身决定了它后面的三个硬伤。

Token：模型处理文字的最小单位。模型不直接读「字」或「词」，而是先把文本切成 token。粗略估算：中文大约一个汉字占一到两个 token，英文一个常见单词占一到两个 token。精确数字要以各家模型的 tokenizer 为准，但记住量级就够用了：一份一万字的文档大约是一万到两万 token。

建立一点直觉：一本 300 页的技术书，按每页 500 字算，大约 15 万字，折算下来是二十多万 token。一本小册子级别的产品手册，几万字，就是几万到十几万 token。这两个数字后面算账时会用到。

上下文窗口（Context Window）：模型一次能「看到」的 token 总量上限，包括你发给它的和它要生成的。窗口大小因模型而异，从几万到上百万 token 都有，比如智谱在 2026 年发布的 GLM-5.2 已经支持 100 万 token 上下文。窗口再大也是有限资源，这一点后面会反复用到。

幻觉（Hallucination）：模型生成看似合理、实则错误内容的现象。现场一就是典型。幻觉不是 bug，是机制的副产品——模型的天职是「生成通顺的续写」，而不是「保证内容属实」。这两个目标大部分时候一致，不一致的时候，幻觉就来了。

知识截止（Knowledge Cutoff）：训练数据的时间边界。边界之后的信息，模型一概不知。现场二的病根。

检索（Retrieval）与生成（Generation）：RAG 名字里的两个主角。检索是从一堆资料里把相关内容找出来的动作，搜索引擎干的就是这件事；生成是模型组织语言产出答案的动作。一个管「找」，一个管「说」，RAG 系统的所有设计，归根结底都是在安排这两件事怎么配合。

为什么会这样：参数化记忆的天生局限

三个现场看似无关，病根是同一个：模型的知识全部以参数化记忆的形式存在。

训练的过程，是把海量文本中的统计规律压缩进模型的万亿个参数里。训练一结束，参数就固定了。这意味着：

知识一旦过期，没法局部更新。想让模型知道上周的新闻？没有「修改某个参数」这种操作，只能重新训练或用别的方式喂给它。

知识没见过的，不会就是不会。你的公司文档、个人笔记、内部系统里的数据，从来没进过训练语料，参数里自然没有。

不记得的时候照样生成。模型没有「这个问题我不知道」的内部开关。它的工作机制是续写最合理的文本，「不知道」这三个字只有在训练语料里常与某类问题一起出现时，才可能被接出来。

和参数化记忆相对的另一个概念叫非参数化记忆：知识不压缩进模型参数，而是存放在外部（数据库、文档库、搜索引擎），用的时候现查。人类的类比是「背书」和「查资料」的区别。RAG 的奠基论文（Lewis 等人，2020）正是用这组对立概念来定义自己的：把参数化记忆（模型本身）和非参数化记忆（可检索的外部知识库）组合起来，各取所长。记住这组概念，它能帮你理解后面很多设计决策。

所以幻觉、时效性、私域知识这三个硬伤，不是靠等下一代模型就能消失的。它们需要的是工程手段，而这正是本章的三种解法。

解法一：Prompt Engineering——把知识塞进提示词

最直接的思路：模型不知道，那我告诉它不就行了。

你向模型提问时发过去的那段文字叫 Prompt（提示词）。在 Prompt 里把相关背景、资料、要求一并写上，模型就能基于这些内容回答。问报销制度？把制度全文复制到问题前面。问新闻？把新闻原文贴进去。

这种做法叫 Prompt Engineering（提示词工程）——通过设计输入来引导模型输出。一个典型的「注入知识」的 Prompt 长这样：

你是公司的行政助手。请仅根据下面的《差旅制度》回答问题，
制度中没有的信息请明确说不知道，不要编造。

《差旅制度》
住宿标准：一线城市每晚不超过 500 元，其他城市每晚不超过 350 元。
……（此处省略若干条）

员工的问题：我去三线城市出差，住宿标准是多少？

模型拿到这样的输入，大概率会给出忠实于制度的答案。它有几个明显的好处：零训练成本，改一段文字就生效；知识随时更新，今天贴今天的资料；行为完全透明，模型看到什么你也看得到。

但它的天花板也很清楚，就是上下文窗口。前面算过账：一份三百页的产品手册，二十多万 token，塞不进大多数模型的窗口；就算塞得下，每次提问都带着整本手册跑，响应变慢，费用按 token 计价的账单也会迅速变得难看。更不要说你手头有几十份这样的手册时，「该贴哪几页」这个问题本身，你还得先手动找到相关内容。都手动找到了，还要模型干嘛？

所以 Prompt Engineering 适合的是：知识量小、更新频繁、你能明确知道该给模型看什么的场景。它是三种解法里最轻的一个，也是每个用模型的人都已经在用的。

解法二：Fine-tuning——把知识训进参数

另一个思路：既然知识在参数里，那就继续训练，把新知识训进去。

Fine-tuning（微调） 是在预训练模型的基础上，用你自己的数据再做一轮小规模训练，调整模型参数。训练数据通常是几百到几万条「输入 → 期望输出」的样例，一条长这样：

{"messages": [
  {"role": "user", "content": "把这句话转成工单格式：打印机又坏了"},
  {"role": "assistant", "content": "{\"类型\": \"设备故障\", \"设备\": \"打印机\", \"优先级\": \"中\"}"}
]}

模型在这些样例上反复学习，逐渐把「见到这类输入就这么输出」变成自己的习惯。这里顺带补一个你大概率会听到的词：早期的微调要调整模型的全部参数，成本高得离谱；现在主流的做法是 LoRA 这类参数高效微调——冻结原模型，只训练一小撮新增的参数，把成本砍掉一两个数量级。LoRA 让微调变得平民化了，但它改变的是微调的「价格」，不是微调的「能力边界」：下面这些「不擅长灌知识」的判断，对 LoRA 同样成立。

微调确实能让模型「学会」新东西，而且在很多场景效果出色：

让模型稳定输出特定格式，比如永远返回符合你公司规范的 JSON；让模型掌握某种风格或口吻，比如客服话术、法律文书腔；让模型熟悉领域术语的用法，比如医疗、金融场景里的行话怎么接。

但用微调来「灌知识」，恰恰是它最不擅长的用途，原因有三。

一是贵且慢。准备训练数据、跑训练任务、评估效果，整个周期以天计，成本以千元计，和改一段 Prompt 完全不是一个量级。

二是知识更新跟不上。每次资料有变动就要重新训练一轮。对周报、文档这种天天变的内容，这条路走不通。

三是会挤掉旧知识。微调是在原参数上继续调整，新数据灌多了，模型原有的通用能力会退化，这叫灾难性遗忘。灌得越多，忘得越多。

一句话总结微调的定位：它擅长教模型「怎么做事」，不擅长教模型「知道什么事」。

解法三：RAG——让模型开卷考试

现在看第三种思路，也是本课的主角。

回到现场三。你要的不是模型「背下」报销制度，而是它能「答对」关于报销制度的问题。这两件事有本质区别。考试时记住整本书是一种办法，开卷考、允许翻书是另一种办法，后者对记忆的要求低得多，需要的只是会查。

RAG 就是这个「开卷考试」思路的工程实现。它的全称是 Retrieval-Augmented Generation，检索增强生成：回答之前，先去资料库里检索出和问题最相关的内容，把这些内容连同问题一起交给模型，让它基于检索到的资料生成答案。

名字有点绕，拆开来读就顺了：用「检索」来「增强」「生成」。这个概念因 Facebook AI 研究团队 2020 年发表的一篇论文（Lewis 等人，NeurIPS 2020）而广为人知，论文把「可检索的外部知识库」和「生成模型」组合成一个系统，在知识密集型任务上明显超过了纯生成模型。今天大家说的 RAG 在工程形态上已经比那篇论文丰富得多，但核心思想没变：模型负责理解和表达，资料库负责记忆和事实。

对照三个硬伤，RAG 恰好各打一枪。先把一次问答的过程在脑子里过一遍：员工问「出差住宿标准是多少」，系统接到问题后，先去文档库里把和「住宿标准」最相关的几段制度翻出来，然后把这些段落和员工的问题一起发给模型，模型读完资料组织语言，最后员工看到答案，答案旁边还标着出自《差旅制度》第几条。注意模型从头到尾没有「背」过制度，它只是现场读了查到的那几段。

具体对应关系是这样的：

幻觉：答案有资料兜底，模型的工作从「凭记忆编」变成「照着资料说」，胡说的空间被大幅压缩。时效性：资料库随时可以更新，今天的新闻今天入库，模型不需要重新训练。私域知识：你的文档、笔记、内部手册，全都可以进资料库，模型参数见没见过它们根本无所谓。

还有一个实际的好处：答案可以注明出处。因为答案是基于具体某几段资料生成的，系统可以把这几段资料一并展示给你。能溯源的答案，可信度完全不一样。

顺带交代一下这项技术的来路。2020 年 Lewis 等人的论文提出时，大模型还没进入大众视野，RAG 只是 NLP 学术界的一种架构思路。转折点在 2022 年底 ChatGPT 爆火之后：无数团队兴冲冲地想把大模型用在自己的业务上，然后齐刷刷撞上了本章开头那三个硬伤。大家发现 RAG 是当时成本最低、见效最快的补救方案，于是它迅速从论文里的架构变成了大模型落地的标准配置。这几年工程实践又把它往前推了好几代：从最简单的「检索加生成」，到加入混合检索、重排序、查询改写的优化形态，再到 GraphRAG、Agentic RAG 这些更复杂的变体。这条演进线，正好就是本课模块一和模块二的路线。

三种解法正面对比

三种解法不是竞争关系，是分工关系。看透了会发现，它们的区别归根到底是一件事：知识放在哪。Prompt Engineering 把知识放在每次请求的输入里，Fine-tuning 把知识压进模型参数里，RAG 把知识留在模型外面的资料库里。存放位置不同，更新成本、容量上限、可溯源性这些性质就全跟着不同了。把关键维度摆在一起看：

维度Prompt EngineeringFine-tuningRAG
知识放哪每次请求的提示词里模型参数里外部资料库里
知识更新改文字，立即生效重新训练，以天计更新资料库，分钟级
单次成本几乎为零训练一次数百到数千元资料库建设 + 每次检索的开销
知识容量受上下文窗口限制受训练数据和遗忘问题限制几乎无上限
可溯源性好（资料就在提示词里）差（知识混在参数里）好（可标注出处）
擅长的事小体量、明确的知识注入格式、风格、术语、行为模式大体量、常更新、需溯源的事实知识

怎么选，看你要解决的问题是什么性质：

flowchart TD A["你要解决什么问题？"] --> B{"让模型学会某种格式、风格或行为？"} B -- "是" --> C["优先考虑 Fine-tuning"] B -- "否" --> D{"需要它知道的内容量小且固定？"} D -- "是" --> E["Prompt Engineering 直接塞"] D -- "否" --> F{"内容量大、常更新、或需要溯源？"} F -- "是" --> G["RAG"] F -- "都不沾" --> H["回到 Prompt Engineering 先试"]

拿一个具体的例子走一遍这棵树。公司想做一个 HR 政策问答机器人：资料是两百份制度 PDF，内容几个月就会修订一批，员工问「陪产假有多少天」时，回答必须能附上制度原文。第一条分叉：不是格式风格问题，往下走；第二条：两百份 PDF 显然不是小体量，往下走；第三条：量大、常更新、要溯源，全中，答案是 RAG。同时「回答的语气要正式、分点列出」这种要求，用 Prompt Engineering 顺手就解决了。微调？这个场景里没有它的位置。

真实项目里三者经常混着用。再举三个典型的组合方式：

客服机器人：产品文档、售后政策用 RAG 管（内容多、常更新、回答要能给用户看依据）；「先安抚情绪再给方案」的话术风格用 Prompt Engineering 约束；投诉工单的 JSON 格式如果怎么调 Prompt 都不稳定，再考虑微调固化。

合同审查助手：法条和过往案例走 RAG（必须溯源，审查意见要注明依据哪条哪款）；「按公司模板输出风险清单」这种稳定的格式要求，值得用一批样例做微调。

本课的实战项目「个人笔记助手」：笔记内容全部走 RAG，不做任何微调，因为笔记天天在变，而你想要的只是「能查到、能答对、能看原文」。

可以看到规律：RAG 管知识，Prompt Engineering 管「怎么把检索结果组织好、把回答要求说清楚」，微调只接管那些稳定、重复、格式化的行为。学完本课你会对「RAG + 提示词工程」这套组合非常熟，因为 RAG 系统的后半截，本质上就是一场精心设计的 Prompt Engineering。

本课路线图与学法

这门课分三个模块，十六个章节。

模块一（第 1–5 章）打地基：搞清楚 RAG 系统的每个零件：全景流程、Embedding、文本分块、向量数据库。模块二（第 6–11 章）上强度：查询改写、混合检索、重排序、生成侧优化、系统评估，以及 GraphRAG、Agentic RAG 这些前沿形态。模块三（第 12–16 章）动手交付：从零做出一个「个人笔记助手」，把你的文档灌进去，用自然语言提问，流式返回答案并标注出处。

几点学法建议：

每一章都有能亲手跑的东西。原理章里的实验别跳过，RAG 这个领域「听说懂了」和「亲眼看到检索结果变化」是两回事。代码示例默认用智谱的免费模型（GLM-4.7-Flash 和 embedding-3，2026-07 核验），国内可以直接调通；用 OpenAI 或本地模型的同学，第 2 章会讲怎么只改配置就切换。前置要求不高：会命令行，能读懂 TypeScript 代码。数据库部分从「会写 SELECT」起步，pgvector 完全从零讲。

RAG 都在哪些业务里用

知道了是什么，再看看它长在各种产品里的样子，你对「学这个能干嘛」会有实感。

企业知识库问答，是最经典的形态。员工不再翻内网的几百份文档，直接问「出差审批要几级领导签字」「这个项目的风控红线是什么」，系统答完附上制度原文。SaaS 化的产品里，这类「知识库 + 问答」几乎是标配功能。

智能客服。把产品手册、售后政策、历史工单喂给系统，机器人回答「这个型号支持以旧换新吗」时有凭有据，答不了的转人工。和早年关键词匹配的客服机器人比，体验完全是两个时代。

垂直行业助手。法律助手基于法条和判例回答，回答注明依据哪条哪款；医疗助手基于诊疗指南和药品说明书作答，出处就是医生的二次核对入口。这类场景对可溯源的要求是刚性的，RAG 几乎是唯一可行的路子。

AI 编程助手里的代码库检索。你让助手改代码，它先去整个仓库里检索相关的文件片段，再基于这些片段生成修改。你熟悉的很多编程工具，底层就藏着一个针对代码优化的 RAG。

本课的实战项目属于个人知识管理这个形态：把自己的笔记和资料灌进去，随手问，随手查原文。麻雀虽小，上面这些产品共享的骨架——检索、生成、溯源——它一个不缺。

三个常见误区，先打预防针

误区一：上下文窗口都上百万了，RAG 没必要了。 窗口变大确实缓解了塞不下的问题，但另外两笔账没变：把一百万 token 塞进每次请求，慢且贵；「从一百万 token 里找出相关内容」这个检索问题也并没有消失，只是从「塞不下」变成了「找不准、看得贵」。窗口变大让 RAG 和「全量塞入」的边界移动了，但没有取消这个边界。第 9 章讲 Token 预算时会把这笔账算细。

误区二：RAG 是微调的一种。 完全两条路。微调改的是模型参数，RAG 压根不动模型，动的是模型的输入。一个是改脑子，一个是给参考书。

误区三：上了 RAG 就不会幻觉了。 RAG 压缩了幻觉的空间，没把它清零。检索不到相关内容时模型可能硬答，检索到了它也可能不照着说。第 9 章的引用溯源和拒答策略、第 10 章的评估方法，就是专门对付这些残留幻觉的。

误区四：RAG 就是买个向量数据库接上模型。 向量数据库是 RAG 的重要组件，但只是一环。检索质量好不好，取决于文档怎么切、查询怎么写、结果怎么排；答案质量好不好，还取决于资料怎么组装、模型怎么约束。把 RAG 当成「买个组件就完事」的项目，大多死在「检索倒是能跑，就是答不准」上。这门课会用模块二整整六章对付「答不准」这件事。

小结与自测

这一章你拿到了三个东西：三个硬伤的名字（幻觉、时效性、私域知识）和它们的共同病根（参数化记忆）；三种解法的分工（Prompt Engineering 管轻量注入，Fine-tuning 管行为风格，RAG 管事实知识）；以及 RAG 的一句话定义：先检索资料，再让模型基于资料生成答案。

如果只能记住一张图，就记这个：三种解法对应知识的三种存放位置：输入里、参数里、模型外的资料库里。位置决定性质：更新成本、容量上限、能不能溯源，全都是位置的函数。以后遇到任何「让模型知道点什么」的需求，先问一句「这知识该放哪」，选型的答案通常自己就浮出来了。

用下面几道题检查一下自己，答不上来的回去翻对应小节：

  1. 同事说「我们直接把产品手册微调进模型吧」，你会从哪几个角度劝他再想想？
  2. 一个 FAQ 机器人，问答对总共 50 条、一个月改一次，你会选哪种解法？一个要基于公司几千份技术文档回答问题的助手呢？
  3. 用「开卷考试」的类比向一个不懂技术的同事解释 RAG，你会怎么说？闭卷考试对应的又是哪种模式？
  4. 为什么说幻觉是机制的副产品，而不是可以修掉的 bug？
  5. 「参数化记忆」和「非参数化记忆」各指什么？RAG 把哪一个交给了模型，哪一个交给了外部？
  6. 有人拿「现在的模型上下文窗口有一百万 token」来论证 RAG 已经过时，你的反驳要点是什么？
