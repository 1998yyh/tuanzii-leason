第 3 章 Embedding 与语义检索：把文字变成可计算的距离

一句话总结：搞懂向量为什么能表示语义、余弦相似度在算什么、大规模数据怎么做到毫秒检索，学会 Embedding 模型的选型方法。

从一个检索失败的案例开始

假设你在做一个电商客服的知识库检索，库里有一条答案：「退货流程：签收后 7 天内可在订单页申请退货，运费由商家承担。」

用户问：「怎么退款？」

如果用传统的关键词匹配——把文档拆成词，看查询里的词在不在文档里——这条答案根本不会被命中。「退款」和「退货」字面完全不同，一个共享的字都没有。用户明明问的就是这条答案，系统却报告「没找到」。

这个失败不是巧合，是关键词匹配的天花板：它只认识字面，不认识意思。而人类的语言里，「同一个意思、完全不同的说法」是常态：退款和退货、住酒店和住宿、电脑卡了和系统运行缓慢。上一章的实验你已经见过另一种可能：「住酒店一晚最多能报销多少」一个关键字都没对上，却精准命中了住宿标准。靠的就是本章的主角：Embedding 和语义检索。

语义检索的世界观：文字即坐标

Embedding（嵌入） 是把一段文字映射成一串数字的技术，这串数字叫向量（Vector），数字的个数叫维度（Dimension）。负责做这件事的模型叫 Embedding 模型：输入一段文本，输出一个向量，比如智谱 embedding-3 默认输出 2048 个浮点数。

单看这个数字串，人什么也读不出来。它的意义不在自身，而在相互位置。把所有文本的向量想象成一个巨大的坐标系里的点：语义相近的文本，点与点离得近；语义无关的，离得远。「退款」和「退货」在坐标系里是邻居，「退款」和「天气」隔着大半个空间。

Embedding 模型不是被人手工规定「哪个词该挨着哪个词」的，而是在海量文本上训练出来的。训练的思路（极度简化版）：让模型看无数对文本，语义相关的就要求它们的向量靠近，不相关的就要求远离，反复调整参数直到模型学会把「意思」编码进坐标里。你不需要会训练它，就像你不需要会造地图也能用导航，重要的是理解地图的性质：距离即语义。

这个思路其实有个很朴素的验证方式。语言学家有个观察：一个词的含义，可以从它经常和什么词一起出现推断出来——「退款」和「退货」出现的上下文高度相似（订单、申请、审核、到账），和「天气」的上下文八竿子打不着。Embedding 模型本质上就是把「上下文分布的相似性」规模化地学习进了向量。所以它能处理你从没教过它的同义说法：只要两种说法活在相似的语境里，它们的坐标就会自然靠近。也所以它对刚冒出来的专有名词、内部代号常常力不从心——训练语料里没见过这些词的语境，坐标就只能瞎猜。这个盲区第 7 章会回来补。

一旦接受「文字即坐标」的设定，检索就从一个语言问题变成了一个几何问题：把问题也变成一个点，找离它最近的几个文档点，完事。这个转变是整个 RAG 的地基。

稠密向量与稀疏向量

Embedding 模型产出的这种向量有个专门的名字：稠密向量（Dense Vector）。说它「稠密」，是因为它的每一个维度几乎都是非零的小数，2048 个数字一个都不浪费，语义被压缩分布在所有维度上。没有任何一个维度单独对应某个词或某个含义——意义是「弥散」在整个向量里的。

和它相对的是稀疏向量（Sparse Vector）：维度巨大（可能等于词表大小，几万维），但绝大多数维度是零，只有少数维度有值，每个维度往往直接对应一个词。你熟悉的「这个词在文档里出现了几次」式的表示，就是稀疏向量的思路。

拿个迷你例子感受两种向量的气质差异。假设词表只有六个词：[退款， 退货， 订单， 天气， 空调， 申请]，那么「申请退款」这句话的稀疏向量是 [1, 0, 0, 0, 0, 1]——词出现过对应位置就是 1（或词频），其余全是零。「退货申请」的稀疏向量是 [0, 1, 0, 0, 0, 1]。两句话意思几乎一样，稀疏向量却只有一个位置重合，像两条岔开的路。而稠密向量不问字面：这两句话的稠密向量会紧紧挨在一起，因为 Embedding 模型看的是语义。一个按「词」记账，一个按「意思」定位，这就是两种世界观的差别。

对比项稠密向量稀疏向量
代表方案Embedding 模型（embedding-3、bge-m3 等）TF-IDF、BM25 等关键词统计方法
维度几百到几千，几乎全非零几万起步，绝大多数是零
单个维度的含义不可解释通常对应具体的词
擅长语义相近、字面不同的匹配精确词、专有名词、编号的匹配
盲区对没见过的专有名词可能「差不多就行」对同义表达完全无感

这一章和下一章的主场是稠密向量。稀疏向量不是被淘汰的旧技术，第 7 章讲混合检索时你会发现，它和稠密向量是互补的两条腿。现在先记住这组对照。

余弦相似度：方向比长短重要

有了向量，就要回答「怎么算两个向量有多近」。RAG 里最常用的度量是余弦相似度（Cosine Similarity）：把两个向量看成从原点出发的两支箭，比较它们方向的夹角。方向完全一致，相似度为 1；方向垂直（八竿子打不着），为 0；方向相反，为 -1。

用二维的玩具例子手算一遍。假设「退款」的向量是 [3, 1]，「退货」是 [2, 1]，「天气」是 [-1, 3]：

余弦相似度 = (a·b) / (|a| × |b|)

退款 vs 退货：
  点积 a·b = 3×2 + 1×1 = 7
  |a| = √(3²+1²) ≈ 3.16，|b| = √(2²+1²) ≈ 2.24
  相似度 ≈ 7 / (3.16×2.24) ≈ 0.99    ← 几乎同向，语义极近

退款 vs 天气：
  点积 = 3×(-1) + 1×3 = 0
  相似度 = 0                            ← 互相垂直，毫无关系

为什么用夹角而不是直线距离？为了公平。一段一百字的长文和一句十个字的短句，如果语义相同，我们希望它们被判为「一样」。长文的向量「更长」（绝对值更大），但方向一致；余弦相似度只看方向不看长短，长短的差异被消掉了。

上一章写的那个 cosineSimilarity 函数，现在回头看就明白了：dot 是点积，normA、normB 是两个向量的长度，返回的就是夹角的余弦值。当时照抄的公式，现在它每个符号你都能说出含义。

实验：亲手算一张相似度矩阵

道理讲完，用真实模型验证一下。新建 embedding-lab.ts：

import "dotenv/config";
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.LLM_API_KEY,
  baseURL: process.env.LLM_BASE_URL,
});

const sentences = [
  "怎么申请退款",                 // 0
  "退货的流程是什么",             // 1（和 0 同义不同字）
  "发票抬头写错了能改吗",         // 2（同属售后，不同问题）
  "今天天气怎么样",               // 3（完全无关）
  "How do I get a refund",       // 4（跨语言同义）
  "办公室空调坏了找谁修",         // 5（无关）
];

// 一次性批量向量化（复习第 2 章的批量技巧）
const res = await client.embeddings.create({
  model: process.env.EMBEDDING_MODEL!,
  input: sentences,
});
const vectors = res.data.map((d) => d.embedding);

function cosineSimilarity(a: number[], b: number[]): number {
  let dot = 0, normA = 0, normB = 0;
  for (let i = 0; i < a.length; i++) {
    dot += a[i] * b[i];
    normA += a[i] * a[i];
    normB += b[i] * b[i];
  }
  return dot / (Math.sqrt(normA) * Math.sqrt(normB));
}

// 打印第 0 句和其他所有句子的相似度
for (let i = 1; i < sentences.length; i++) {
  const score = cosineSimilarity(vectors[0], vectors[i]);
  console.log(`${score.toFixed(3)}  「${sentences[0]}」 vs 「${sentences[i]}」`);
}

跑 npx tsx embedding-lab.ts。具体数字随模型版本浮动，但排序结构会相当稳定，大致是：

0.8x   「怎么申请退款」 vs 「退货的流程是什么」
0.7x   「怎么申请退款」 vs 「How do I get a refund」
0.5x   「怎么申请退款」 vs 「发票抬头写错了能改吗」
0.2x   「怎么申请退款」 vs 「办公室空调坏了找谁修」
0.1x   「怎么申请退款」 vs 「今天天气怎么样」

盯着这个结果看一分钟，它把本章的全部论点都演示了一遍。同义不同字的「退货」排第一，证明了语义检索不是字面游戏；跨语言的英文问法紧随其后，说明模型把不同语言的相同语义放进了坐标的同一片区域；「发票」同属售后场景但问的是另一件事，拿到一个「沾边但不命中」的中间分。这个中间地带以后会给检索排序带来麻烦，第 8 章的重排序就是对付它的；两句无关的话被压到了底部。

有对照才有说服力。在同一个文件里补几行，模拟一下关键词匹配面对同样句子的表现：

// 关键词匹配的最简模拟：查询里的每个字，在句子里出现了几个
function keywordScore(query: string, doc: string): number {
  let hit = 0;
  for (const ch of query) if (doc.includes(ch)) hit++;
  return hit;
}

console.log("关键词得分：");
for (let i = 1; i < sentences.length; i++) {
  console.log(`${keywordScore(sentences[0], sentences[i])}  「${sentences[0]}」 vs 「${sentences[i]}」`);
}

「退货的流程是什么」和查询「怎么申请退款」只有一个「退」字重合，得分和无关句子拉不开差距；「发票」那句反而因为「请」「款」等字的巧合拿到不相称的高分。字面重合与否，和语义相关与否，基本是两回事，这就是开篇那个客服案例翻车的机理。

你可以再把打印改成全矩阵（两两都算），或者换几句你自己业务里的真实问法试试。亲手调一调、看一看，比读十页解释都管用。

// 全矩阵版本：两层循环，两两计算
for (let i = 0; i < sentences.length; i++) {
  const row = sentences.map((_, j) =>
    cosineSimilarity(vectors[i], vectors[j]).toFixed(2)
  );
  console.log(`[${i}]`, row.join("  "));
}

对角线全是 1.00（和自己完全同向），矩阵沿对角线对称，如果跑出来不是，说明你的相似度函数写错了。这也是一个顺手验证代码正确性的办法。

相似度多高才算「相关」

实验里自然引出一个问题：检索时该把相似度多少以上的块送给模型？

没有通用答案，只有几条经验。同一模型的分数分布是稳定的，所以阈值要在你自己的数据上实测出来：拿几十个真实问题跑检索，观察「命中」和「没命中」的分数各落在什么区间，阈值定在两者之间。不同模型的分数绝对值不能直接比较：A 模型的 0.6 可能比 B 模型的 0.7 更「严」。相似度是排序的好工具，但作为「是否相关」的绝对判据，它比较勉强。这正是第 8 章引入重排序模型的原因之一：让专门的模型来打「相关与否」的分。

百万级数据怎么毫秒检索：ANN 与 HNSW

我们的实验只有六句话，暴力两两比对毫无压力。把规模换成一百万个文档块，每次查询要和一百万个向量各算一次余弦，一次检索就要好几秒，显然不行。

工程上的解法是ANN（Approximate Nearest Neighbor，近似最近邻）：不再保证找到「数学上最近」的那几个，而是用一点精度换巨大的速度——找到「几乎肯定在最近的那批里」的结果，耗时从秒级压到毫秒级。注意「近似」两个字：ANN 是有召回率代价的，可能漏掉个别真正相近的向量。实际系统里这个代价通常很小（召回率 95% 以上），换来的速度收益是几个数量级。

ANN 索引的主流实现是 HNSW（分层可导航小世界图）。它的直觉可以这样建立：把所有向量点组织成一张多层的「高速公路网」——最上层只有稀疏的几个远距离枢纽，越往下层点越密。查询时从顶层进入，先跳到离目标最近的枢纽，再逐层下降、逐步逼近，像在地图上先走高速、再转国道、最后进小巷。大部分点根本没被访问到，这就是快的原因。

现在你只需要记住两件事：ANN 用微小的召回率换取数量级的速度；HNSW 是最常用的 ANN 索引，建索引、调参数的事第 5 章在 pgvector 里实操（到时候你会见到 m、ef_construction 这两个参数，它们分别控制图的连接密度和建索引时的搜索宽度，都是「速度、内存、召回率」三角上的旋钮）。

Embedding 模型也有输入上限

聊天模型有上下文窗口，Embedding 模型同样一次吃不了太长的文本，常见上限是几百到八千 token，因模型而异。超长的输入要么被接口拒绝，要么被悄悄截断，后半部分等于白算。

就算没超上限，把一篇两万字的文档整个塞进去算一个向量，效果也很差：文档里讲了十件事，十层语义被平均成一个坐标，这个坐标离哪件事都不太近、也不太远。检索时问哪件事都匹配不准。这叫语义稀释。

所以「先把长文档切成聚焦的小块，再逐块向量化」是 RAG 的刚需步骤，也是下一章的全部内容。现在先建立因果关系：Embedding 的输入上限和语义稀释，决定了分块必须存在。

Embedding 模型选型

模型选错，上层怎么优化都补不回来。选 Embedding 模型看四个维度：

考量要问的问题
语言能力你的语料是中文、英文还是混合？跨语言检索要不要支持？
向量维度维度高通常表达力强，但存储和计算成本线性上涨
成本API 按 token 计费（智谱 embedding-3 约 0.5 元/百万 token，2026-07 核验）；本地模型零调用费但要吃自己的机器
隐私文档能不能出内网？不能就只能本地部署

维度这笔账值得算细一点，因为它直接决定你的数据库要长多大。一个 float32 浮点数占 4 字节，一条向量的存储就是「维度 × 4 字节」：

维度单条向量100 万条向量
512约 2 KB约 2 GB
1024约 4 KB约 4 GB
2048约 8 KB约 8 GB

这还没算 ANN 索引本身的开销（HNSW 的图结构通常再增加两三成）。个人项目随便选，上了规模，维度就是一个要和真金白银挂钩的决策。

主流的几种选择：

智谱 embedding-3：本课默认。中文场景表现好，默认 2048 维且支持自定义维度（调小维度能直接省存储和算力），价格便宜，国内直连。

OpenAI text-embedding-3-small / large：国际场景的主流选择，同样支持自定义维度。用 OpenAI 的同学直接沿用，接口和第 2 章完全一致。

BGE-M3 等开源模型：北京智源研究院（BAAI）出品的开源 Embedding 模型，多语言能力出色，可以本地部署——数据不出本机，零调用费。本地跑它的最简单方式是用 Ollama：装好 Ollama 后执行 ollama pull bge-m3，然后按第 2 章的方法把 EMBEDDING_BASE_URL 指向 http://localhost:11434/v1、模型名填 bge-m3 即可，代码一行不改。本地模型的代价是要自己扛机器配置，Embedding 模型对显卡要求不高，CPU 也能跑，就是慢一些。

想看客观对比，可以查 MTEB（Massive Text Embedding Benchmark）榜单（Hugging Face 上维护）。它是 Embedding 模型的「考试成绩单」，按检索、分类、聚类等任务分别打分。读榜单时别只看总排名：重点看和你场景匹配的任务分项（做中文检索就看中文检索分），以及榜单数据的新旧——这个领域模型迭代很快。

把上面的考量落到三个典型场景，选型结论通常长这样：

场景推荐理由
个人笔记、中文资料为主，想零门槛跑通智谱 embedding-3中文好、便宜、免折腾
面向海外用户的产品OpenAI text-embedding-3 系列多语言稳定、生态配套全
内网部署、文档涉密bge-m3 本地部署数据不出网，零调用费

当然它们可以混搭：开发和原型期用免费便宜的 API 快速验证，量起来或合规收紧了再迁本地。只要记住换模型必须重建索引，迁移就是一道工序而不是一堵墙。

三个常见误区

误区一：向量是原文的加密或压缩。 都不是。从向量推不回原文，它不是可逆的编码；它也不负责节省空间，2048 个浮点数比原文那段话占的存储多得多。向量是「语义的坐标」，只为「算距离」这一件事服务。

误区二：换 Embedding 模型，旧向量还能接着用。 绝对不行。向量只在产出它的那个模型的坐标系里才有意义。A 模型算出的「退款」向量，在 B 模型的坐标系里就是一堆随机数。换模型等于换地图，所有存量向量必须用新模型全部重算，这叫重建索引。选模型时要意识到这个切换成本，别频繁横跳。

同一个供应商也要留个心眼：API 侧的 Embedding 模型会升级换代，老型号会退役。型号名写死在配置里、升级时统一重建索引，是生产环境的基本纪律。这也是我们把模型名放在 .env 而不是代码里的另一个理由。

误区三：维度越高越好。 在合理范围内，高维度确实通常带来更强的表达力，但收益递减，而存储、内存、计算成本是线性涨的。支持自定义维度的模型，可以实测几个档位（比如 512 / 1024 / 2048），在自家数据上找到「质量不掉、成本砍半」的甜点。第 10 章的评估方法会给你实测的手段。

语义检索的边界：它不是万能钥匙

吹了一整章，必须诚实地画一条边界。回到前面那句「上下文分布相似则坐标相近」——反过来说，训练语料里语境稀少的文本，坐标就不可靠。哪类文本中招最多？

精确标识符：错误码 E1002、型号 XPS 13 9340、订单号、法条编号「第 1032 条」。这些东西的含义不来自语境，来自定义本身。搜「E1002 怎么解决」时，语义检索可能觉得 E1002、E1003、E2001「都差不多」，毕竟它们在语料里出现的语境确实很像。但对用户来说，差一个字符就是完全不同的错误。

新词和内部黑话：公司项目代号、社区刚流行的梗、上个月才发布的产品名。训练语料没见过它们，坐标约等于随机分配。

这类「字面必须精确」的需求，恰好是关键词检索的主场。所以工业实践里，向量检索很少单打独斗，而是和关键词检索组队——这叫混合检索，第 7 章专门讲。现在记住判断标准就够了：查询依赖语义泛化，用稠密向量；查询依赖字面精确，稠密向量会漏，需要稀疏检索补位。

小结与自测

本章是模块一的理论核心，你拿到了：语义检索的世界观（文字即坐标，距离即语义）；稠密与稀疏向量的分工；余弦相似度的原理和手算能力；ANN/HNSW 的存在意义（近似换速度）；Embedding 模型的选型框架（语言、维度、成本、隐私）和两条纪律（分数跨模型不可比、换模型必须重建索引）。
