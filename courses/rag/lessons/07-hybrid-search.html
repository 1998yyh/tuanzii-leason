第 7 章 混合检索：BM25 + 向量的多路召回

一句话总结：看清向量检索的字面盲区，搞懂 BM25 的原理直觉，用 RRF 融合实现向量 + 关键词的混合检索。

badcase 现场：向量检索的字面盲区

第 3 章埋过一笔账，现在还。假设你的运维知识库里有这么几条：

① 错误码 E1002 表示数据库连接池耗尽，应检查连接泄漏并调大池上限。
② 错误码 E1003 表示数据库连接超时，应检查网络与慢查询。
③ 错误码 E2001 表示磁盘空间不足，应清理日志目录。
④ XPS 13 9340 笔记本升级 BIOS 前必须接电源并关闭 BitLocker。
⑤ 每周五 18:00 执行例行维护，期间服务只读。

用户问：「E1002 怎么解决？」

向量检索在这里的表现很微妙：E1002、E1003、E2001 三条在语义空间里几乎是邻居（都是「错误码 + 数据库/磁盘 + 怎么办」的句式，上下文分布高度相似），①②③ 的相似度分数挤在一起，Top1 是 ① 还是 ② 基本看运气。答错一个字符，就是完全不同的事故处理。

用户对错误码、型号、法条编号这类精确标识符的要求是「一字不差」，而稠密向量的世界观是「意思相近就好」。这不是调参能修的，是世界观层面的不匹配。第 3 章说的稀疏检索，该它上场了。

稀疏检索的世界观：倒排索引

关键词检索为什么能精确命中 E1002？因为它按词记账。核心技术是倒排索引（Inverted Index）：把每个词映射到「包含它的文档列表」。

E1002  → 文档①
E1003  → 文档②
错误码  → 文档①②③
连接   → 文档①②

查询「E1002 怎么解决」到来时，先拆成词，然后查倒排表：含 E1002 的只有文档①，候选集瞬间收敛。字面精确性就是这么来的——词不匹配，文档连候选都进不了。

但「进候选的怎么排名」是另一门学问。文档①里 E1002 出现一次，文档②里如果出现五次（假设），②就更相关吗？文档越长越占便宜吗？给这套排名一个靠谱的打分公式，就是 BM25 干的事。

BM25 原理：三个因子

BM25 是关键词检索最经典的打分函数（TF-IDF 家族的现代形态，Elasticsearch、Lucene 的默认打分器）。不用背公式，看懂三个因子各自管什么：

score(文档, 查询) = Σ  IDF(词) × TF饱和(词频, 文档) × 长度归一(文档)
                      └┬─┘   └────┬────┘   └───┬───┘
                    这词多稀罕  出现了几次    文档多长

因子一：IDF，词越稀罕越值钱。 「的」「是」出现在所有文档里，区分度为零；E1002 只出现在一篇文档里，一锤定音。IDF 就是给每个词按「在多少文档里出现过」打分：越稀有的词，命中时贡献越大。这就是错误码查询如此锐利的原因。

因子二：TF 饱和，词频收益递减。 一个词出现 1 次和 3 次，相关性有差别；出现 30 次和 33 次，几乎没差别。BM25 用饱和曲线（参数 k1 控制陡峭程度，默认 1.2）把词频的贡献压平，防止堆词作弊——早年 SEO 在页面里塞几百遍关键词骗排名的把戏，在 BM25 面前无效。

因子三：长度归一，长文不白占便宜。 同样出现一次「超时」，一百字的短文档比一万字的长文档更「切题」。BM25 用文档长度与平均长度的比值（参数 b 控制力度，默认 0.75）做归一，长文档得分被打折。

手算一个迷你例子建立直觉。语料就三篇：D1「E1002 连接池耗尽」（5 词），D2「E1003 连接超时」（5 词），D3「连接池与连接超时都是连接问题的常见形态，连接问题需要逐个排查」（21 词）。查询「E1002」：

IDF(E1002)：3 篇里只有 1 篇含它 → 很稀罕，高分
D1：含 E1002 → 得分 = IDF × TF饱和 × 长度归一 ≈ 高
D2：不含 E1002 → 0 分
D3：不含 E1002 → 0 分（尽管它「连接」浓度最高）

查询换成「连接」：D3 词频最高但篇幅最长，长度归一把它的得分压下来，和 D1、D2 的差距没有想象中大——三个因子各自起作用的现场。

稠密 vs 稀疏：失败模式对照

第 3 章给过两种向量的气质对照，现在从「各自怎么死」的角度再看一次：

查询类型稠密向量稀疏（BM25）
「退款」搜「退货」（同义不同字）轻松命中直接漏掉
「E1002」（精确标识符）和 E1003 混排一锤定音
「出差住一宿报几个钱」（口语）大体稳住拆词后可能颗粒无收
「第 1032 条规定了什么」（编号）容易张冠李戴精确命中
训练语料没见过的新词坐标约等于随机只要字面在就能中
拼错一个字（「E1002」打成「E1O02」）可能还认得出直接归零

两列的失败模式几乎完美互补：你弱的我强，我弱的你强。这就是为什么工业界的主流答案不是二选一，而是混合检索（Hybrid Search）——两路召回，各取所长。

混合检索的架构

flowchart LR Q["用户问题"] --> V["向量路<br/>Embedding + pgvector"] Q --> B["关键词路<br/>BM25"] V --> F["融合排序<br/>（RRF）"] B --> F F --> T["统一 TopK<br/>交给生成环节"]

查询同时走两条路：向量路按语义召回一批，BM25 路按字面召回一批，融合后得到统一的 TopK。错误码查询靠关键词路兜底，口语化查询靠向量路兜底，大多数查询两路各自贡献一部分好结果。

融合的难题：两路分数根本不可比

合并不是简单的「两个列表拼一起」。麻烦在于分数：向量路交出的是余弦距离（0 到 2 之间的小数），BM25 路交出的是 BM25 分（0 到几十，上不设限，还随语料变化）。量纲不同、分布不同，直接比大小毫无意义——BM25 的 8 分和向量距离的 0.3，谁更「相关」？

有人想过归一化（各自缩放到 0–1 再加权），但两路分数的分布形状完全不同，强行归一经常把 BM25 路的头部结果压到不合理的位置，调权重又是个玄学活。

RRF：不看分数，只看名次

RRF（Reciprocal Rank Fusion，倒数排名融合） 用一个特别朴素的方式绕开了分数不可比：既然分数没法比，那就只比排名。公式：

RRF得分(文档) = Σ  1 / (k + 该文档在各路结果中的名次)
              每一路

k 是平滑常数，常用 60。意思是：某文档在向量路排第 1，得 1/(60+1)≈0.0164；在 BM25 路排第 3，得 1/(60+3)≈0.0159；两路得分相加就是它的总分。

手算一遍。向量路排名是 [①, ③, ②]，BM25 路排名是 [②, ①, ⑤]：

①：1/(60+1) + 1/(60+2) = 0.0164 + 0.0161 = 0.0325
②：1/(60+3) + 1/(60+1) = 0.0159 + 0.0164 = 0.0323
③：1/(60+2) + 0        = 0.0161
⑤：0        + 1/(60+3) = 0.0159

融合排名：① > ② > ③ > ⑤

注意两个性质。第一，两路都排前的文档会冒头（①② 都进了两路前两名，总分甩开单路结果一大截）——这正是「两路投票」想要的效应。第二，k=60 让名次之间的差距被压得平缓：第 1 名和第 5 名的单路得分只差约 20%，不会因为某一路把不相干结果排在第一就彻底主导排序。这就是为什么 RRF 比加权分数融合稳——它对所有「分数分布不可知」的场景都免疫，工程上是混合检索的默认答案。

k 的作用可以再细品一下。k 越小（比如 10），头部名次的优势越大，融合结果越「听第一名的话」；k 越大，名次间差距越平，融合结果越像「平均投票」。k=60 是论文和工程实践里常用的默认值，背后的考量是：既让两路共同认可的结果稳定胜出，又不让任何一路的头部失误一票定音。这个值对你的场景是否最优，第 10 章的评估集可以给出答案——k 也是可调的参数，不是魔法数。

实操：手写 BM25，跑通完整混合检索

动手把整套链路实现一遍。生产环境的 BM25 一般用搜索引擎（Elasticsearch/OpenSearch）或数据库扩展（PostgreSQL 的全文检索）来做，但为了看清机制，先用 40 行 TypeScript 手写一个——和第 2 章手写向量检索同一个思路：先懂，再用现成的。

新建 bm25.ts：

// 超简化中文分词：按 2 字滑动窗口切（生产用 jieba 或数据库的分词扩展）
function tokenize(text: string): string[] {
  const cleaned = text.replace(/[^\p{L}\p{N}]/gu, " ").toLowerCase();
  const tokens: string[] = [];
  for (const word of cleaned.split(/\s+/)) {
    if (!word) continue;
    if (/^[a-z0-9]+$/.test(word)) { tokens.push(word); continue; } // 英文数字整词
    for (let i = 0; i < word.length - 1; i++) tokens.push(word.slice(i, i + 2)); // 中文双字
    if (word.length === 1) tokens.push(word);
  }
  return tokens;
}

export class BM25 {
  private k1 = 1.2;
  private b = 0.75;
  private docs: string[][];
  private avgLen: number;
  private df = new Map<string, number>(); // 每个词出现在几篇文档里

  constructor(private rawDocs: string[]) {
    this.docs = rawDocs.map(tokenize);
    this.avgLen = this.docs.reduce((s, d) => s + d.length, 0) / this.docs.length;
    for (const doc of this.docs) {
      for (const term of new Set(doc)) {
        this.df.set(term, (this.df.get(term) ?? 0) + 1);
      }
    }
  }

  private idf(term: string): number {
    const n = this.df.get(term) ?? 0;
    const N = this.docs.length;
    return Math.log(1 + (N - n + 0.5) / (n + 0.5)); // BM25 的 IDF 形式
  }

  scoreAll(query: string): number[] {
    const terms = tokenize(query);
    return this.docs.map((doc) => {
      let score = 0;
      for (const term of terms) {
        const f = doc.filter((t) => t === term).length; // 词频
        if (f === 0) continue;
        const lenNorm = 1 - this.b + (this.b * doc.length) / this.avgLen;
        score += this.idf(term) * ((f * (this.k1 + 1)) / (f + this.k1 * lenNorm));
      }
      return score;
    });
  }
}

对照前面的三个因子读这段代码：idf 函数是因子一；f * (k1 + 1) / (f + k1 * lenNorm) 是因子二的饱和曲线；lenNorm 是因子三。分词是最简的双字滑动窗口——「错误码」会被切成「错误」「误码」，查询和文档都按同样的规则切，匹配照样成立。

双字窗口有个已知缺陷，值得想清楚：它切不出真正的词。「苹果手机」被切成「苹果」「果手」「手机」，查询「苹果牌手机」切成「苹果」「果牌」「牌手」「手机」——两边共享「苹果」「手机」，照样能匹配（这正是 n-gram 的容错性）；但「果手」「牌手」这类伪词也会参与打分，带来噪声。n-gram 的好处是永远不会「切错词」、对任何语言零配置可用；坏处是精度不如真分词。生产环境的中文检索用 jieba、IK 这类真分词器，把「苹果手机」切成「苹果/手机」两个干净的词，噪声少得多。教学用 n-gram，是因为它把「分词对 BM25 的影响」这件事直接暴露在你眼前。

RRF 融合同样手写，十行：

// rankings：每一路的「文档下标按名次排列」数组
function rrf(rankings: number[][], k = 60): Map<number, number> {
  const fused = new Map<number, number>();
  for (const ranking of rankings) {
    ranking.forEach((docIdx, rank) => {
      fused.set(docIdx, (fused.get(docIdx) ?? 0) + 1 / (k + rank + 1));
    });
  }
  return fused; // docIdx → RRF 总分，按值排序即最终排名
}

// 用法：向量路排名 + BM25 路排名 → 融合
const vectorRanking = [0, 1, 2];   // 假设向量路认为 ① 最相关（实际由 Embedding 检索给出）
const bm25Ranking = [1, 0, 4];     // BM25 路认为 ② 最相关
const fused = rrf([vectorRanking, bm25Ranking]);
console.log([...fused.entries()].sort((a, b) => b[1] - a[1]));

完整项目里，向量路的排名来自第 5 章的 pgvector 查询，BM25 路来自上面的实现或数据库全文检索，两路排名喂给 rrf，出来的就是交给生成环节的 TopK。

生产路径：BM25 不一定要手写

手写是为了懂机制，真实项目有更趁手的家伙：

PostgreSQL 全文检索：tsvector / tsquery 自带关键词匹配能力，和 pgvector 同库，两路召回可以在一个库里完成。英文场景开箱即用：

-- 英文直接可用：建立检索列并查询
SELECT content, ts_rank(to_tsvector('english', content), query) AS rank
FROM chunks, to_tsquery('english', 'connection & timeout') query
ORDER BY rank DESC LIMIT 5;

但有一个中文的坑要提前知道：自带的 simple 配置按非字母数字切分，中文整句会被当成一个 token，必须装中文分词扩展（zhparser、pg_jieba 等）或对中文做预处理。打分函数 ts_rank 是 TF-IDF 家族而非严格 BM25，对大多数场景够用。单库方案对中小项目吸引力很大。

Elasticsearch / OpenSearch：BM25 的原生主场，中文配 IK 分词器，功能最全，代价是多维护一套搜索集群。

专用向量库的混合能力：Qdrant、Weaviate 等也纷纷内置了稀疏向量（如 BM25 的向量形态 SPLADE）混合检索，如果你本来就用了专用库，可以少搭一套。

实战项目（第 12–16 章）为了保持架构简单，先用纯向量检索上线，混合检索作为第 16 章复盘的扩展方向——到时候你对「加这条路要解决什么 badcase」会有非常具体的判断标准。

何时不值得上混合

混合检索不是免费的：多一路召回，多一份索引维护、多一倍检索时延、多一套调参。这几种情况可以暂缓：文档量很小（几百块以内），badcase 还没有出现；查询以自然语言长句为主（客服闲聊式提问），精确标识符很少；语料是代码、日志之外的普通文本，向量路 already 稳。

判断标准永远来自 badcase：第 10 章的评估集跑下来，「精确标识符类查询」的命中率明显拖后腿，就是该上混合检索的信号。没有信号就上，是过度设计。

常见误区

误区一：混合检索就是两个分数加权平均。 前面算过账，量纲不同、分布不同，加权融合是玄学。RRF 只看名次，是更稳的默认选择。

误区二：关键词检索过时了。 它只是不擅长语义，在精确匹配主场仍然无敌。把它和向量对立起来是 2023 年最流行的误判之一。

误区三：上了混合就不管分词了。 中文 BM25 的效果七分在分词。「错误码」被切错，后面的打分公式再漂亮也白搭。生产环境换分词器/扩展时，先拿 badcase 集回归一遍。

小结与自测

本章把检索从一条腿变成两条腿：向量检索的字面盲区（标识符混排）与 BM25 的三个因子（IDF 稀罕度、TF 饱和、长度归一）；混合检索的两路架构；分数不可比问题与 RRF 的名次融合；手写 BM25 + RRF 的完整实现与生产路径（PG 全文检索 / ES / 专用库）。

自测：

  1. 用 BM25 的三个因子解释：为什么「E1002」的检索效果远比「连接问题」锐利？
  2. RRF 为什么比加权分数融合更稳？k 调大调小分别影响什么？
  3. 双字滑动窗口分词有什么缺陷？（提示：想想「苹果手机」和「苹果牌手机」）生产上怎么解决？
  4. 向量路 Top1 和 BM25 路 Top1 不是同一个文档时，RRF 会怎么处置？这体现了什么设计思想？
  5. 你的个人笔记助手用户主要在问「我上次记的那个 pgvector 参数叫什么」，该上混合检索吗？依据是什么？

检索把正确答案捞回来了，但捞回来的 50 个候选里，它可能只排第 7——而 Prompt 只放得下前 3 个。下一章的重排序，就是把第 7 名捞到第 1 名的技术。
