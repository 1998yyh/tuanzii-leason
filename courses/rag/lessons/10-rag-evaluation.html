第 10 章 RAG 系统评估：没有度量就没有优化

一句话总结：建立检索与生成双线评估体系，学会构建评估集、用指标说话、靠 badcase 驱动迭代。

从一场玄学优化开始

工程师小张觉得自家 RAG 不太准，把 chunk size 从 500 调到 300，问了三个问题，感觉答案顺眼了，宣布优化成功，上线。一周后用户投诉变多——他调参后试的那三个问题，恰好是小块占便宜的类型；他从来没试过的那几百种问题里，一大批在变差。

这个故事的每个环节都很眼熟：凭感觉定方向、凭三个问题下结论、凭记忆做回归。RAG 系统的可调旋钮太多了——chunk size、TopK、混合与否、重排模型、阈值、Prompt 写法——每个旋钮都可能让一部分问题变好、另一部分变差。没有评估，优化就是掷骰子，赢了都不知道怎么赢的。

这一章建立完整的工作方式：先用指标把「好不好」变成可测量的数字，再用评估集保证测量覆盖真实分布，最后用 badcase 归因把「哪里差」翻译成「修哪个部件」。

先拆开：检索质量和生成质量是两回事

RAG 系统的失败有三种独立的形式：该捞的没捞到（检索漏）；捞到了但排不进前列（检索错）；捞到排好了，模型没用好（生成错）。三种失败对应不同的责任部件，混在一起测一个「总分」，永远不知道该修哪。

所以评估的第一原则是双线分开：

flowchart LR subgraph 检索线["检索线评估（不看答案）"] Q1["问题"] --> R["召回列表"] --> M1["召回率 / MRR / NDCG"] end subgraph 生成线["生成线评估（看最终答案）"] R --> A["模型答案"] --> M2["忠实度 / 相关性"] end

检索线只问「正确答案在不在召回结果里、排第几」，和模型怎么答无关；生成线只问「答案忠不忠于资料、有没有回答到点子上」。一个系统完全可能检索线 95 分、生成线 60 分——那就是 Prompt 组装和指令的问题，别去动检索。

检索指标：三个就够

Recall@K（召回率）：所有该被捞到的相关块里，有多少进了前 K 名。例：某问题有 2 个相关块，Top5 里出现了 1 个，Recall@5 = 50%。它回答「有没有漏」——检索漏不漏，看它。

MRR（Mean Reciprocal Rank，平均倒数排名）：第一个相关块排第几的倒数，再对所有问题取平均。相关块排第 1 得 1 分，排第 2 得 1/2，排第 5 得 1/5。它回答「正确答案排得够不够前」——正好对应第 8 章「Top3 命中率」的焦虑。手算：三个问题的首个相关块分别排第 1、3、5，MRR = (1 + 1/3 + 1/5) / 3 ≈ 0.51。

NDCG（Normalized Discounted Cumulative Gain，归一化折损累计增益）：最精细的一个——既看相关性分级（非常相关 2 分、沾边 1 分、无关 0 分），又给排名位置打折（越靠后折扣越大），最后用「理想排序」归一化到 0–1。它回答「整个排序离完美有多远」。排序里不只有「中/不中」两种状态时用它，比如混合检索调参对比。

NDCG 手算一个小例子。某问题的三块相关度标注是：块A=2 分（直接答案）、块B=1 分（沾边）、块C=0 分（无关）。你的系统排出 [B, A, C]，理想排序是 [A, B, C]：

DCG（你的排序）：B在第1位: 1/log2(2) ≈ 1.00
                A在第2位: 2/log2(3) ≈ 1.26
                C在第3位: 0/log2(4) = 0
                合计 ≈ 2.26
IDCG（理想排序）：A在第1位: 2/log2(2) = 2.00
                B在第2位: 1/log2(3) ≈ 0.63
                合计 ≈ 2.63
NDCG = 2.26 / 2.63 ≈ 0.86

排第一的如果是 A（正确答案），NDCG 就是满分 1。位置越靠前的高分块对总分贡献越大——「好结果排前面」被直接编码进了公式。

三个指标的分工：Recall@K 管漏不漏，MRR 管前不前，NDCG 管整体排序质量。日常迭代盯 Recall@K 和 MRR 就够用，NDCG 留给细活。

生成指标：忠实度是生命线

Faithfulness（忠实度）：答案里的每个论断，能不能被检索到的资料支撑。这是 RAG 的头号指标——它直接度量第 1 章的核心命题「照着资料说，还是凭记忆编」。测量方法（LLM 当裁判版）：把答案拆成若干论断，逐条问裁判模型「这个论断能被资料支持吗」，统计支持率。

Answer Relevancy（答案相关性）：答案有没有真正回应问题。忠实但答非所问的答案（问住宿标准，答了一通报销流程）在这项上丢分。常见测量法：让裁判模型根据答案反推「它像在回答什么问题」，再和原问题算相似度。

Context Precision / Context Recall（上下文精度/召回）：这一对其实是评估「检索结果对生成够不够用」的桥接指标——交给模型的那几块资料里，有效的占多少比例（精度）、答案需要的信息有没有全部包含（召回）。它帮你区分「检索给的料不行」和「模型没把料用好」。

评估集：指标的地基

指标再好，没有靠谱的评估集都是空转。评估集就是一批「问题 + 标准答案（或相关块标注）」，构建有两条路：

人工标注：从真实文档出发，人工写问题和答案。质量最高，覆盖最真实，但慢——攒 50 条要几个小时。冷启动必须靠它，哪怕只有 30 条。

LLM 合成：让模型读文档块，自动生成问答对。合成 prompt 的关键是「限定题型」，否则收上来的全是千篇一律的「什么是 X」：

阅读下面的文档块，生成 3 个问答对：
1. 一个事实直给型问题（答案直接在块中）。
2. 一个口语化的问题（模拟真实用户不那么严谨的问法）。
3. 一个需要结合块中两处信息才能回答的问题。
输出 JSON：[{"question": "...", "answer": "...", "type": "..."}]

【文档块】
……

一天能造几百条，但有三个坑：合成问题同质化严重；答案可能本身就是模型编的（用幻觉评估幻觉）；和真实用户的问法有差距（真实用户更口语、更含糊）。正确姿势是合成 + 人工抽检 + 逐步用真实用户问题替换。

规模与构成的经验值：起步 30–50 条就能暴露大头问题；覆盖要刻意多样——事实直给型、跨块综合型、口语化、带指代的、精确标识符类（第 7 章的盲区）、以及一定比例的「库里没有答案」的问题（测拒答，很多人漏掉这类）。评估集要跟着业务长：每次线上发现 badcase，修复后把它收进评估集，防止同一个坑摔两次。

一份及格的评估集条目长这样（基于第 7 章的运维语料）：

问题类型相关块标注期望行为
E1002 报错怎么处理精确标识符块①命中①并给出处理步骤
笔记本升级 BIOS 要注意什么事实直给块④答出接电源、关 BitLocker
磁盘满了清什么目录口语转述块③答出日志目录
错误码和例行维护分别是什么时间跨块综合块③⑤综合两块作答
数据库连不上但报的是 E1002，要不要重启网络陷阱（块①没让重启网络）块①忠实于①，不附和错误前提
服务器怎么装显卡驱动库外问题无拒答

注意「陷阱题」和「库外题」——它们测的不是「答得多好」，而是「不越界」，这恰是 RAG 最值钱的行为。

用 LLM 当裁判：便宜但有偏差

忠实度、相关性这些生成指标，人工评最准但最贵，工业界的折中是 LLM-as-Judge：让强模型按 rubric 打分。一个忠实度裁判 prompt 长这样：

给定【资料】和【答案】，把答案拆成独立论断，逐条判断该论断
能否被资料直接支持。输出 JSON：
{"verdicts": [{"claim": "...", "supported": true/false}]}
忠实度 = supported 为 true 的比例。

用之前必须知道它的三个偏差：位置偏差（并列展示的多个答案，裁判偏爱先出现的）；自我偏好（用 A 模型生成的答案，A 模型当裁判容易打高分——裁判和被测最好用不同模型）；宽松偏差（裁判倾向于「大体对就算对」，比人工松）。这些偏差不能消除，但可以控制：成对比较时交换顺序跑两遍、裁判固定用同一强模型、定期抽人工校准。LLM 裁判的价值是「便宜的一致性」，不是「绝对的正确性」——同一个裁判下，版本 A 比版本 B 高 5 个点，这个相对比较是可信的。

忠实度裁判的最小实现（TypeScript，和本课主线一致）：

type Verdict = { claim: string; supported: boolean };

async function faithfulness(context: string, answer: string): Promise<number> {
  const resp = await client.chat.completions.create({
    model: process.env.LLM_MODEL!,
    messages: [
      {
        role: "system",
        content:
          "把【答案】拆成独立论断，逐条判断能否被【资料】直接支持。" +
          "只输出 JSON：{\"verdicts\":[{\"claim\":\"...\",\"supported\":true}]}",
      },
      { role: "user", content: `【资料】\n${context}\n\n【答案】\n${answer}` },
    ],
    response_format: { type: "json_object" }, // 约束输出为合法 JSON
  });
  const { verdicts } = JSON.parse(resp.choices[0].message.content!) as { verdicts: Verdict[] };
  return verdicts.filter((v) => v.supported).length / verdicts.length;
}

response_format: { type: "json_object" } 是结构化输出的开关，智谱和 OpenAI 的兼容接口都支持——裁判输出必须能稳定解析，否则一次跑 50 条样本，总有几次 JSON 解析爆炸。这也是第 1 章说的「微调管格式」的轻量替代：能靠接口参数解决的格式问题，先别动模型。

现成的轮子：RAGAS

不想手写裁判流水线的话，RAGAS 是这个领域最知名的开源评估框架：内置 Faithfulness、Answer Relevancy、Context Precision/Recall 等指标的成熟实现，喂给它「问题 + 检索上下文 + 答案」，它跑完裁判流程给出各项指标分数。它的主战场是 Python 生态（pip install ragas），几行代码就能对一批评估样本出分：

from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy

result = evaluate(dataset, metrics=[faithfulness, answer_relevancy])
print(result)  # 每个指标的得分表

本课主线是 TypeScript，所以评估 harness 我们自己写（就是上面那些裁判 prompt 的组合，几十行代码）；团队在 Python 生态或想要成熟实现的话，RAGAS 值得直接用。指标定义两边完全一致——学完本章，你看 RAGAS 文档会毫无障碍。

把评估跑成流水线

零散指标要组装成可重复执行的 harness，才能支撑「改一次、跑一次、看一次」的节奏。骨架如下：

type EvalCase = { question: string; relevantSeqs: number[]; expectRefuse?: boolean };

async function runEval(cases: EvalCase[], ragAnswer: (q: string) => Promise<RagResult>) {
  const rows = [];
  for (const c of cases) {
    const result = await ragAnswer(c.question);       // 你的完整 RAG 链路
    const recall = c.relevantSeqs.filter((s) =>
      result.retrievedSeqs.includes(s)
    ).length / (c.relevantSeqs.length || 1);
    const firstHit = result.retrievedSeqs.findIndex((s) => c.relevantSeqs.includes(s));
    const rr = firstHit === -1 ? 0 : 1 / (firstHit + 1);
    const faithful = c.expectRefuse
      ? (result.refused ? 1 : 0)                       // 库外题：拒答即满分
      : await faithfulness(result.context, result.answer);
    rows.push({ q: c.question, recall, rr, faithful });
  }
  // 汇总：均值 + 最差 5 条（别只看平均，误区二）
  console.table(rows);
  const avg = (k: "recall" | "rr" | "faithful") =>
    rows.reduce((s, r) => s + r[k], 0) / rows.length;
  console.log(`Recall=${avg("recall").toFixed(2)} MRR=${avg("rr").toFixed(2)} Faith=${avg("faithful").toFixed(2)}`);
}

这个骨架故意写得朴素：没有并发控制、没有缓存、没有报告美化。但它把评估的本质动作全固定下来了——同一份评估集、同一条链路、同一组指标、每次产出可对比的数字。你的每个优化 PR，都应该附一份它跑出来的前后对比。

实验：三个版本，一张成绩单

把模块二的优化史变成一次评估实验。用同一套评估集（比如基于你的实验文档造 20 条 QA），分别喂给三个版本：

版本配置
V1 naive第 2 章形态：向量检索 Top3，朴素 Prompt
V2 +混合检索向量 + BM25，RRF 融合后 Top5
V3 +重排V2 基础上加 Cross-Encoder 精排

跑完在评估集上记分（这是示例结构，你的数字要自己跑出来）：

版本Recall@5MRR忠实度备注
V10.620.550.81标识符类问题大面积漏召回
V20.850.630.83召回上来了，但 Top3 里仍有噪声
V30.850.790.88MRR 大涨——重排把答案顶进前列

三个数字讲三个故事：V1→V2，Recall 涨，是混合检索补上了字面盲区；V2→V3，Recall 不动 MRR 涨，是重排在召回不变的前提下改善了排序；忠实度一路小涨，是因为交给模型的料越来越干净。每个优化手段的贡献被量化得清清楚楚——以后再有「我觉得这个优化有用」的讨论，把这张表拍出来。

badcase 驱动迭代：评估的日常形态

版本发布不是评估的终点，日常迭代长这样：

收集：线上日志里捞低赞答案、用户追问三次还没解决的对话、以及主动抽检。

归因：每个 badcase 按固定三分法定责——检索漏（相关块没进候选）？检索错（进了候选但排不到前列）？生成错（料给足了模型没用好）？第 4 章的「先查块、再查向量、最后查模型」就是归因的具体动作。

定向修复：检索漏 → 查分块/Embedding/召回路数；检索错 → 查重排/融合参数；生成错 → 查 Prompt 组装/指令。每个部件修自己的病，不乱动别的旋钮。

回归：修复后全量跑评估集，确认 badcase 消除且总分没掉；把这个 badcase 收编进评估集。

这个循环第 16 章项目复盘时会以真实形态再走一遍。

常见误区

误区一：指标涨了就是系统好了。 指标只测量评估集覆盖的分布。针对评估集反复调参，会把它「调穿」——分数涨了，真实分布上没动，这叫评估集过拟合。对策：定期换血（加入新的真实问题）、留一部分从不用于调参的「压轴题」。

误区二：平均分掩盖一切。 MRR 0.8 可能是「全都排 1.25 名」，也可能是「八成满分、两成垫底」——后者意味着两成用户天天在吃烂答案。看分布，看最差的那批问题，别只看均值。

误区三：评估是上线前的一次性仪式。 模型会升级、文档会更新、用户问法会漂移。评估集和评估动作是要跟着系统一起活的，上线后定期回归才是常态。

小结与自测

本章把「优化靠信仰」升级成「优化靠数据」：失败三分法与双线评估（检索漏/检索错/生成错各归各的部件）；检索三指标（Recall@K 管漏、MRR 管前、NDCG 管排序质量）；生成指标以忠实度为生命线；评估集构建的两条路（人工冷启动 + LLM 扩量）与 LLM 裁判的三个偏差；三版本对比实验与 badcase 归因循环。

自测：

  1. 「Top3 命中率低但 Recall@20 很高」，病灶在检索线还是生成线？该动哪个部件？
  2. MRR 和 Recall@K 分别在第 8 章重排的哪个价值点上给出量化证明？
  3. 用 glm-4.7-flash 生成的答案，用 glm-4.7-flash 当忠实度裁判，会有什么偏差？怎么缓解？
  4. 评估集里为什么要专门放「库里没有答案」的问题？没有它们会漏掉什么？
  5. 同事连续三周针对评估集调参，MRR 从 0.6 涨到 0.85，用户投诉却没降。最可能的解释是什么？

评估体系就位，优化从此有据可依。模块二还剩最后一章：当经典 RAG 撞上天花板（全局性问题、多步推理），GraphRAG 和 Agentic RAG 这两条路各自通向哪里。
